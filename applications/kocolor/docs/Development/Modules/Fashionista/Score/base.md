This is **much closer to the right architecture**, given the clarification that FASHIONISTA is **not a recommendation engine**. It is a standalone, deterministic **outfit aesthetic evaluator**: give it an outfit, get one number.

However, I would make several important changes before calling this the production specification.

### The biggest conceptual change

I would define FASHIONISTA as:

> **FASHIONISTA Score = a deterministic computational estimate of the overall aesthetic coherence, sophistication, balance, and visual integration of an observed outfit, independent of whether KoColor recommended, owns, or recognizes any of its items.**

That distinction is crucial.

The engine should have **no concept of "should wear," candidate retrieval, missing roles, wardrobe optimization, or user preference**.

Its input is simply:

**Observed Outfit → Features → Subscores → Unified Score**

```text
OUTFIT
  │
  ├── Garments
  ├── Shoes
  ├── Accessories
  ├── Cosmetics
  └── Optional wearer/image

        ▼
```

## I would NOT use the current GCN/MLP wording as-is

This is the biggest issue.

You said:

> **All this must be code that can run without an LLM**

That's fine.

But a **pre-trained neural network is still a machine-learning model**. It is not an LLM, but it also isn't truly deterministic mathematical scoring in the sense your architecture appears to want.

If FASHIONISTA is supposed to be:

* local
* offline
* deterministic
* reproducible
* explainable
* one-number output
* no LLM
* no cloud dependency

then I would make the **core scoring engine mathematical**, not dependent on a GCN whose weights need to be trained somewhere.

You can still use neural networks later for *feature extraction* if you want, but the actual FASHIONISTA number should be generated by a deterministic scoring function.

# The architecture I would use

I'd actually expand your four pillars into a stronger computational model:

### 1. Composition — `S_composition`

Does the outfit make structural sense?

Measures:

* category relationships
* proportion
* layering
* repetition
* visual hierarchy
* accessory relationships
* footwear/garment grounding
* semantic coherence

### 2. Color — `S_color`

Does the palette work?

Measures:

* CIELAB / LCh
* CIEDE2000
* hue relationships
* chroma distribution
* lightness distribution
* temperature coherence
* neutral handling
* accent color relationships
* palette complexity

### 3. Silhouette & Proportion — `S_silhouette`

Does the visual shape work?

Measures:

* vertical distribution
* horizontal distribution
* visual mass
* center of visual gravity
* upper/lower balance
* silhouette ratios
* layering density
* negative space
* symmetry/asymmetry
* intentional focal point

### 4. Material & Texture — `S_texture`

Does the surface composition work?

Measures:

* texture frequency
* texture complexity
* pattern density
* material relationships
* texture repetition
* contrast between materials
* visual noise
* order/complexity relationship

### 5. Visual Hierarchy — `S_hierarchy`

This is something I think your current formulation is missing.

A great outfit generally has:

**primary → secondary → tertiary**

visual elements.

For example:

```text
Statement coat       ██████████
Dress                ███████
Shoes                ████
Jewelry              ██
```

Rather than:

```text
Coat      ████████
Dress     ████████
Shoes     ████████
Bag       ████████
Jewelry   ████████
Pattern   ████████
```

The second outfit can become visually chaotic even if every pair of colors is technically compatible.

### 6. Integration — `S_integration`

This evaluates whether the **whole thing reads as one intentional visual system**.

This is where:

* clothing
* accessories
* shoes
* makeup
* hair
* skin/face when available

come together.

# One particularly important correction

I would **not** call the output a "percentile."

Your current equation:

> sigmoid → 0–100 percentile scale

is misleading.

A score of **87** does not necessarily mean:

> "This outfit is better than 87% of all outfits."

Unless you actually calibrate against a worldwide reference population and establish that interpretation.

Instead:

> **FASHIONISTA 87/100**

means the outfit achieved an 87 on the FASHIONISTA aesthetic scale.

That's much cleaner.

```text
0.0000 — 1.0000
```


This gives you reproducibility and allows future calibration without changing the engine.

# The really important part: make it deterministic

I would make the public API extremely simple:

```kotlin
interface FashionistaScorer {

    fun score(
        outfit: FashionistaObservation
    ): FashionistaScore
}
```

And:

```kotlin
data class FashionistaScore(
    val score: Double,          // 0.0–100.0
    val confidence: Double,
    val breakdown: FashionistaBreakdown
)
```

The breakdown can contain:

```kotlin
data class FashionistaBreakdown(
    val composition: Double,
    val color: Double,
    val silhouette: Double,
    val texture: Double,
    val hierarchy: Double,
    val integration: Double
)
```

But the **headline remains one number**.

That matches exactly what you're trying to accomplish.

# And I would change the "confidence" concept

Confidence should **not** change the score.

For example:

```text
FASHIONISTA
91

Confidence
0.96
```

is better than secretly reducing 91 because some information wasn't available.

If an outfit photo doesn't contain texture information:

```text
Score:       91
Confidence:  0.71
```

The score represents the computed aesthetic evaluation from available evidence.

Confidence represents how complete/reliable the observation was.

---

# Your missing concept: Reference-free evaluation

This is actually central to what you're describing.

FASHIONISTA should not ask:

> "Is this outfit similar to outfits humans previously liked?"

It should ask:

> **"How strongly does this observed outfit satisfy the computational principles encoded by FASHIONISTA?"**

That means the engine can evaluate:

* something from KoColor
* something from another app
* something bought at a store
* a vintage outfit
* a runway outfit
* a random outfit
* an outfit from another country
* an outfit nobody has ever seen before

without needing the item to exist in KoColor.

That's a very strong architectural property.

---

# One other change I'd make to your color system

Your chroma-weighted circular hue approach is excellent, but don't let it become:

```text
dominant hue = everything
```

You want **palette distribution**, not merely one representative hue.

For example:

```text
Outfit A

Navy       45%
White      35%
Tan        15%
Gold        5%
```

versus:

```text
Outfit B

Red        25%
Green      25%
Blue       25%
Purple     25%
```

Both could have mathematically similar average vectors under some circumstances.

But visually they are radically different.

So I'd retain:

```text
Hue centroid
Hue dispersion
Chroma distribution
Lightness distribution
Color dominance
Accent isolation
Pairwise ΔE00
Template harmony
```

That gives the color engine substantially more information.

---

# And don't make Birkhoff `O/C` literally divide

This:

```text
M = O / C
```

is historically interesting, but computationally dangerous.

If:

```text
C → 0
```

you have an unstable score.

Instead construct normalized features:

```text
Order ∈ [0,1]
Complexity ∈ [0,1]
Texture coherence ∈ [0,1]
Pattern regularity ∈ [0,1]
```

and derive:

```text
S_texture = f(Order, Complexity, Coherence, Regularity)
```

This is much more numerically stable.

---

# Most importantly: don't hard-code "balanced = good"

This is where your current CoG section could accidentally make the engine mediocre.

A runway/editorial outfit can intentionally be:

* asymmetrical
* top-heavy
* oversized
* extremely high contrast
* highly textured
* culturally unconventional

and still be extraordinarily good fashion.

So:

```text
imbalance ≠ bad
```

Instead:

```text
unresolved imbalance = penalty
intentional controlled imbalance = potentially positive
```

That's a much more sophisticated aesthetic model.

The same principle should apply everywhere.
